# 微信小程序审核说明

## 一、这次被拒的原因

审核驳回原文：

> 存在个人主体小程序未开放服务类目，违反《微信小程序平台运营规范常见拒绝情形 2.1》。
> 你的小程序涉及用户自行生成内容（文字、图片）记录、分享，属社交-笔记范畴，
> 为个人主体小程序未开放类目，建议申请企业主体小程序。

**定性：这是主体资质问题，不是 UGC 声明漏填。**

驳回意见里有两个独立的事实：类目不开放（个人主体不能做社交-笔记）、以及本小程序
确实存在用户生成内容的记录与分享能力。两个都成立时，补多少声明文字都不会改变结论 ——
平台看的是主体有没有资格做这个类目，不是你有没有写「内容需审核」。

本轮（以及上一轮）做的所有文案与声明工作，都不能解决这次拒审。它们能解决的是**复审时
不该再因为「没写清楚」被挑出来**。

## 二、三条路线

| 路线          | 做法                                           | 成本         | 能不能过       |
| ------------- | ---------------------------------------------- | ------------ | -------------- |
| A. 换企业主体 | 营业执照 + 300 元认证费，申报「社交-笔记」类目 | 主体迁移成本 | 能             |
| B. 砍掉 UGC   | 本小程序不做用户投稿，钓点只由运营方维护       | 产品形态改变 | 能，但要改实现 |
| C. 只补文案   | 声明写得更全                                   | 零           | **不能**       |

C 是最容易做的，也是最没用的 —— 平台审核员会点进投稿页看是不是真能提交。

**本轮走的是 B 的文案部分**：把声明口径改成「钓点只接受程序所有者提交，其他用户退出」。
B 要完整成立，还需要实现层拦住普通用户（见第五节）。

## 三、企业主体复审会查的五项

换主体后重新提审，下面五项是必查的，任何一项被挑出来都要再走一轮：

1. **类目与实际功能匹配** —— 声明说不开放投稿，实现层就必须真的挡住。
2. **内容审核机制** —— 有审核入口、有驳回理由、有处理记录。
3. **举报入口** —— 用户能举报违规内容，且举报有去向。
4. **隐私政策与实际收集一致** —— 声明说只收位置与账号，代码就不能多收。
5. **UGC 相关的资质材料** —— 企业主体下的运营规范与类目要求。

## 五、还差什么

按「复审前必须完成」排序。

### 1. 实现层拦住普通用户（必须）

声明说「只接受所有者提交」，代码现在还没拦。后端
`internal/service/fishing/spot_write.go` 的 `CreateSpot` 只区分管理员与普通用户
（管理员直接 approved，普通用户进 pending），没有「只有所有者能提交」这层判断。

要成立，得加一道：服务端识别运营方身份，非运营方提交返回 403；前端同步隐藏入口。
**只改文案不改实现，等于对审核员说谎** —— 他会用自己的账号走一遍。

### 2. 举报入口缺「违规内容」一项（大概率会查）

详情页底部只有「信息有误？提交反馈」，语义是纠错。反馈五种类型
（`location_wrong` / `closed` / `fee_wrong` / `info_stale` / `other`）里
没有违规举报。

轻量方案：在反馈类型里加「违规内容」，复用现有端点与后台审核闭环，
后端加一个枚举值。改动落在 `Server-Go`。

### 3. 微信内容安全接口未接入（可解释）

当前纯人工审核，`msgSecCheck` / `imgSecCheck` 都没接。对本项目量级够用，
但复审前宜主动向审核员说明这是人工审核闭环。若要接入，需在 `Server-Go`
加机审调用、access_token 管理与失败降级策略。

### 4. 主体迁移的操作顺序

改主体不是改个字段就完事：

1. 先注册企业主体小程序账号；
2. 把现有代码包、域名、类目在新主体下重新配置；
3. `Server-Go` 的服务地址、微信 AppID/Secret、支付与消息配置全部换；
4. 数据迁移（用户表按 openid 对齐，钓点 owner_id 需要重绑）；
5. 新主体下重新提审。

**顺序别弄反**：先迁移主体再改代码，中间会出现代码指向的主体与后台主体不一致的窗口期。

## 七、本轮：入口与页面称谓改为「钓点投稿」

**改了什么**（只改标签，声明与协议正文一字未动）：

- `SPOT_CREATE_TITLE` / `SPOT_CREATE_LEDE.title` —— `新建钓点` → `钓点投稿`
- `MY_SPOTS_EMPTY_ACTION` —— `去新建钓点` → `去投稿`
- 代码注释与 `docs/` 里的页面称谓同步；`scripts/gen-icons.mjs` 的图标说明改了并重跑
  `pnpm icons`（`src/constants/icons.ts` 是产物，不手改）

**理由**：入口动作的性质是「把信息交给平台、由平台审核后公开」，而不是「自己建一条记录、
立刻就是既成事实」。措辞跟着真实流程走，页面才不承诺它兑现不了的东西。

**⚠️ 但这一轮不改变拒审结论**，理由有三条：

1. 按第二节，路线 C（只补文案）不能过审 —— 平台看的是主体有没有资格做「社交-笔记」类目。
2. 审核员会点进投稿页看能不能提交，而后端 `CreateSpot` 现在对普通用户仍然放行
   （第五节第 1 条未做）。只改文案不改实现，仍然是对审核员说谎。
3. 标题里的「投稿」二字比原来的「新建」更接近 UGC 信号。只有第五节第 1 条做完
   （服务端对非运营方返回 403 + 前端隐藏入口），这一页对普通用户不可达时，改名才有意义。

**因此**：如果第五节第 1 条短期内做不了，标题建议改回不含「投稿」的措辞（如「添加钓点」）——
声明里写着「不开放钓点投稿」，入口却叫「投稿」，审核员更容易在这里停一下。
