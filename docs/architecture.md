# 架构与数据流

## 分层

```
pages/         编排：取数、状态、版式
components/    渲染与交互，不自己取数
composables/   跨组件复用的逻辑（视口、导航栏尺寸、字体、SSE 状态机）
stores/        Pinia 单例：跨页共享的状态
api/           网络层：端点清单的唯一出处
utils/         无状态纯函数
types/         共享类型
constants/     文案与生成物
```

依赖方向单向向下。**组件之间不互相 import** —— 需要共享就提到 store 或 composable。

## 数据流

```
页面 onMounted / onPageShow
  → store 的动作（ensureWeatherAndFishing / fetchSpots / restore）
    → api 模块（fishingApi / fishingSpotApi / streamWeatherAnalysis）
      → client.request → uni.request
        → 后端 { message, data } 信封
```

`client.ts` 负责剥信封、合并 HTTP 错误与网络错误、挂 token。**调用点拿到的就是业务对象**，不用自己剥 `data`。

## 唯一出处

清单在 `AGENTS.md` 的「约定」一节 —— 端点、类型、色值字阶、文案、图标各归一处。

## 钓鱼记录 ≠ 钓鱼反馈

系统里有两套「记录」，**别混**：

|      | 钓鱼反馈                                                 | 钓鱼记录                                   |
| ---- | -------------------------------------------------------- | ------------------------------------------ |
| 端点 | `v2/fishing/feedback`（Python）/ `v3/fish/records`（Go） | `v3/fish/logs`                             |
| 表   | `fishing_record`                                         | `fishing_log`                              |
| 归属 | **没有** —— 匿名可写                                     | **有** —— 绑定 user id                     |
| 内容 | 天气 9 项 + 爆护/好/一般/差/空军                         | 渔获清单、钓法、照片、地点、备注、天气快照 |
| 读   | 没有读端点                                               | 按月取、单条取、统计                       |
| 用途 | 残差模型的**训练集来源**                                 | 用户的**个人日志**（日历打卡）             |

两者刻意不共用一张表：`fishing_record` 的写端点刻意不挂鉴权（ADR 0013 把「记录归属」
列为非目标），而训练样本必须是**同分布**的 —— 往里塞带归属、带图片的个人日志，
会污染残差模型的校准。

### 但它们在同一次提交里

表单只有一张：`pages/record/create/index`（记录新建页）。天气页的「反馈今日鱼口概率」
与记录页的「记一笔」进的是同一页。

- **已登录**：先写记录（`v3/fish/logs`），再写鱼口反馈（`v3/fish/records`）。两次请求，
  两个端点。反馈失败**不回滚记录** —— 记录已经在了，只提示一句，用户可以再反馈一次。
- **未登录**：只剩鱼口反馈那一次请求。记录绑定用户，没有「游客记录」这回事；
  而反馈端点匿名可写，所以游客照样能给今天的鱼口概率表个态。

两件事说的是同一天、同一个地点、同一份气象条件，所以地点与天气只填一次、
发两遍：记录的地点就是反馈的地点，模型校准用的就是用户手改过的那份天气快照
（`utils/feedback.ts` 的 `buildFishingFeedbackPayload` 负责拼载荷与缺值兜底）。

「鱼口体验」这一档必选（渔获为空时默认「空军」并可改）：它是模型唯一的标签来源，
跳过去等于白发一条没有标签的样本。

### 这套记录的口径

- **只支持今天**：`log_date` 必须是服务端当天（Asia/Shanghai），后端直接 400。
  「当时的天气」取的是当下的实时天气，不是历史天气 —— 后端没有历史天气接口，
  静默拿今天的天气填到三天前的记录里，比空着更糟。
- **打卡是派生状态**：一条记录，渔获字段可空。空记录 = 当天打卡；
  当天有记录，日历上就是已打卡。**空打卡每天最多一条**（重复提交幂等返回既有 id）。
- **统计由服务端算**：连续天数与总天数是跨月的量，前端拿一个月的数据算不出来。
  `current_streak` 的口径是**今天没打卡不算断** —— 从今天往回数，今天空着就接着昨天数。
- **渔获清单存 jsonb**：一次出行一条，渔获是 `[{species, quantity}]`。
  同名鱼种**不归一**（「鲫鱼」/「鲫」是两条不同的记录），这是有意接受的代价 ——
  服务端没有鱼种分类表，强行归一就得先有一张表，而用户钓的鱼超出任何固定清单都很常见。
- **只增删，不编辑**：记错了就删掉重记一条。编辑要处理「改了图片怎么办、
  旧图要不要删」，而记录是往回看的东西。
- **地点是选出来的，不是打出来的**：记录页的地点只能从微信选点地图里选，
  不接受自由输入，也不拿「手机此刻在哪」兜底 —— 晚上补记时手机多半已经不在
  钓点上了，那份坐标说的不是钓鱼的地方。没选点就不带位置：一个读不出来源的
  坐标比没有坐标更坏。
- **完全私有**：只有本人能读，不做公开渔获墙。

## 坐标

- 写反经纬度会定位到地球另一侧，但不报错
- 两位小数是**后端的缓存与降级粒度** —— 不要为了「更精确」改成 `toFixed(6)`，位数变了后端缓存全部 miss
- store 用 `locationKey()`（两位小数）比对，同一个坐标就是同一份数据。原地挪几十米不该发请求，换了城市才该重取

## 归一

上游（和风新一代接口）给的是「数值 + 嵌套对象」，组件和 AI 建议载荷要的是**扁平视图模型**。换算全在 `src/utils/weather-normalize.ts` 里做，**在 store 边界调一次**。

组件一行都不用改，后端 `app/schemas/aiagent.py` 认的字段形状也就没变。上游换接口格式时，只改这一个文件。

## 天气码归组

和风的天气现象官方码表是 68 个码（字体子集里存在的那些，见 `src/utils/weather.ts` 的
`SUPPORTED_RANGES` —— 两者逐个对过，一致），但界面上要表现的是十种「看天」的印象：
晴 / 多云 / 夜 / 雨 / 雪 / 雨夹雪 / 尘雾 / 热 / 冷。同组共用一套渐变与字色。

**归组按区间，不按码名。** 和风改过码名：400 这一段在不同版本里是「雪 / 小雪 / 中雪」的不同排法。
按名字写一张映射表，换个版本就对不上；按区间走则与名字无关。

**未覆盖的码走通用样式，不给它专属长相。** 和风官方明说「天气现象和图标将不断的更新，
包括新增、修改和删除」—— 每来一个新码就配一套颜色，配不完；而且配出来的那套永远只是
「我们没见过」的颜色。通用样式只有一条原则：**拿掉天气的颜色，不动天气的信息。**

| 元素     | 通用样式                                                                                                             |
| -------- | -------------------------------------------------------------------------------------------------------------------- |
| 卡面     | 还是那块渐变面（A 原图方案的整块渐变面板），但不带任何天气色 → 中性灰                                                |
| 字色     | 常规墨色，不翻白。通用组是还没认出来的码，不带任何天气的信息 —— 深色面翻白的是夜组，另一回事                         |
| 天气图标 | 999 中性字形。跟 `weatherIconCode()` 的白名单纪律一致，不另开第二套判断                                              |
| 读数     | 照常显示。缺的是外观，不是数据                                                                                       |
| 现象文字 | 用上游给的原文（`text` 字段）。以后新增「冰雹」这类码，字形落 999，文字仍然是「冰雹」—— 不因为没画图标就把信息也丢了 |

三条兜底：

- 码不认识（白名单外）→ 落通用样式。
- 温度 / 最高 / 最低缺一个 → 那项不画，不拼出「--°」「↑ --」这种空壳。箭头是个读数，没有数的时候它会骗人。
- 整块天气数据没有 → 不画那张有读数的卡，走空态（玻璃面里一句「暂无天气数据」）。一片中性灰的「未知」不是「不知道天气」，是「假装知道」。

⚠️ **空态不是加载态 ——「还没取」不能说成「没有」。**

取数有两段：先定位（授权询问 + 一次往返），再发请求。`weatherLoading` 只覆盖第二段，
第一段跑着的时候它还是 false。这时若只看它，卡片会先摆一句「暂无天气数据」，
过几秒才变成骨架、再变成真数据 —— 空态说了假话。

所以两张卡的加载判定都要把 `locating` 算进来：

```ts
const loading = computed(() => mapStore.locating || mapStore.weatherLoading);
```

出错时同样别把「取不到」写成「没有」：卡上写「天气暂时取不到」，
具体原因交给 toast 与结论头那块（`VerdictOverview` 一直摆着），别把后端原文摆到卡上。

⚠️ **「今天」只能有一个出处。**

`CurrentWeather` 的高低温与 `DayForecast` 的「今天」指的是同一天，两边各判一次，
早晚出现一张卡说今天、另一张卡说昨天（接口的第一条要是脏数据就会被丢掉）。
口径收在 `utils/weather.ts` 的 `forecastDays()`：只留高低温都有值的那几天，
「今天」= 留下来的第一条。两张卡都从它取。

**两处出处分工**：

| 出处                                               | 放什么                                                                                                                              |
| -------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `src/utils/weather.ts`                             | `weatherGroup()`：码区间 → 组名（与 `levelTone`、`weatherIconCode` 并排）                                                           |
| `src/utils/weather.ts`                             | `forecastDays()`：有效预报日 —— 两张卡说「今天」的唯一出处                                                                          |
| `src/components/CurrentWeather/CurrentWeather.vue` | 每组外观的四个 CSS 变量：`--weather-grad`（面）、`--weather-ink`（主字色）、`--weather-ink-2`（次字色）、`--weather-icon`（图标色） |

组名是两边唯一的接缝。组件拿组名拼 class 修饰符（`current-weather--rain`），
同名的那条规则给出那套配色 —— 那条规则只改四个 `--weather-*` 变量，
底下的规则一律读 `var()`。

外观表放在组件自己的 `<style scoped>` 里，不进令牌层：令牌层会被 uni.scss 拼到
每个组件的样式前面（见 `src/uni.scss`），规则写在那里会跟着复制到每一个组件的 wxss。
共享的原语（墨色、弱化字色、深色面上的白字）仍然取令牌，组与组之间的差别留在组件里。

⚠️ **接缝是 class，不是属性。** WXSS 不认属性名选择器（见
`docs/mp-weixin-platform.md`「WXSS 的选择器」），`[data-weather='rain']` 写了不报错、
只是不生效。节点上仍然挂着 `data-weather`，那是留给事件用的，不参与选样式。

组名改一处要改两处 —— 拼错组名的表现是「这一组没有专属颜色」（落回通用样式），不会白屏。
通用样式是映射查不到组时的落点，不是一条额外的分支。

## 守卫

几个 in-flight 守卫，同一个道理 —— 同一份数据不该被两个调用方各拉一次：

| 守卫             | 位置                          | 挡的是什么                                                                     |
| ---------------- | ----------------------------- | ------------------------------------------------------------------------------ |
| `locatePending`  | `stores/fishingMap`           | 并发定位。两次定位会弹两次权限窗，拿到两个略有差异的点，表现为「地点名闪一下」 |
| `inflightKey`    | `stores/fishingMap`           | 同一坐标并发取数。两个响应互相覆盖，地点名闪一下                               |
| `restorePending` | `stores/session`              | 并发恢复会话                                                                   |
| `inflight`       | `composables/useQweatherFont` | 并发加载字体                                                                   |

守卫只是最后一道锁。**请求归 store 一家管** —— 组件不要重复触发 store 已经发过的请求：
潮汐曾经是 setter 发一次、组件 watch 再发一次，两个响应先后覆盖同一份数据，
表现为「地点名闪一下」。职责划分（谁负责发）比守卫更根本：守卫只挡并发，不防复发。

## 两个 store

**`fishingMap`** —— 用户坐标、天气、潮汐、鱼口概率、钓点标记、当前选中的钓点、我提交的钓点。

`mySpots`（我提交的）和 `markers`（地图上的）是**两份不同的数据**，不能合成一份：公开列表只放已过审的，`mySpots` 含待审核和已驳回。合成一份的话，待审核那条会在地图上显示出来 —— 它还没过审。

`mySpots` 有两个消费方：「我的钓点」页要清单，「我的」页只要一个数量
（「我手上有几条」「还有几条在审」）。两处都走 store，不各发一次请求。
「我的」页取数是 `fetchMySpots({ silent: true })` —— 取不到就当没数，
不必为一个附属信息弹 toast 打断用户；退出登录时 `clearMySpots()`
把上一个账号的数据清掉，否则登出之后这一页还会显示着别人的条数。

`selectedMarker` 放在 store 而不是地图页的局部 state：选中动作发生在钓点页，消费方却是记录新建页（反馈与记录合成一张表单）—— 跨页只能靠 URL 传，而 URL 带 marker 还得额外处理刷新和失效，不如共享状态直接。

选中态与标记集合是分开的两份，不是合成一个：选中只改一个引用，不该顺带触发地图标记的全量 diff。

**`session`** —— 当前用户、恢复会话、登录、写昵称、传头像、退出。

token 的存取在 `api/client.ts`，401 的静默刷新在 `api/auth.ts`，store 只管状态。

Pinia 装在 `main.ts`，全应用一份，跨页共享没问题 —— 小程序各页面是独立的 Vue 实例，但都挂在同一个 app 上。

选 setup store 而不是 options store：两个 store 里都有天生属于闭包的东西（in-flight 守卫、坐标 watch）。setup store 里它们就是普通局部变量，作用域跟着 store 实例走，不用靠「模块级变量 + 只有一份的约定」来维持唯一性。

## AI 流式

```
FishingAnalysisSheet
  → useFishingAnalysis（状态机 + 120ms 节流）
    → api/ai.streamWeatherAnalysis
      → api/stream.streamSse（协议层）
        → utils/sse（分帧解码）
```

- 节流在 `useFishingAnalysis` 里，不在组件里 —— 「多久刷一次」是数据到达节奏的事，和显示无关
- `stream.ts` 只吐协议层数据（`{ event, data, id, retry }`），data 的具体结构由调用方解析，这一层不做业务假设
- reasoning 与 content 两个通道各自攒着，等同一个定时器一起刷出去
- **思考通道结束不代表正文结束** —— 那时候正文一个字都还没来，只有正文通道的 `is_end` 才算答完
- 主动 `abort()` 不算失败，状态是 `stopped` 而不是 `error`，也不谎称生成完毕
- 发起新的一轮会先掐掉上一轮 —— 连点两次不该有两条流同时写同一个缓冲区

## 组件边界

- 组件读 store，不互相 import
- 页面负责编排：取数、开关浮层、把状态翻译给组件、把结果讲给用户听
- 文案在 `constants`，组件和页面都只管排版
- 浮层统一用 `SnapSheet` 容器

## 审核

钓点的审核在 **Web 后台**（`../kanocifer-chat-frontend` 的 `/admin/fishing-spots`），不在小程序里。

- 后端把普通用户的投稿置为 `pending`，公开列表写死只放 `approved` —— 小程序端因此**看不到**待审队列，也不需要看到
- 管理员专属的 `GET /v3/fish/spots/admin`（按状态查 + 强制分页）只给后台用，小程序不调
- 小程序这一侧只负责**属主自助改稿**：被驳回的条目在「我的钓点」里显示 `review_note`，改完重交 —— 后端会把没过审的退回 `pending` 并清掉备注

两端的状态文案要一致（`待审核 / 已通过 / 未通过`），改一边记得改另一边。

## 已知缺口

这几条是后端契约的现状。接回对应功能时先验：

- **钓点的删除没有 UI** —— 编辑这一半已经接上了（`pages/spot-edit`，属主在「我的钓点」和钓点详情页都能进），删除还留着。删除是破坏性操作，在手机上做需要二次确认与删除理由，代价与收益不匹配，另议。`fishingSpotApi.remove` 端点留着但没有调用方
- **投稿的钓点不会立刻出现在地图上** —— 后端把普通用户的投稿置为 `pending`，公开列表写死只放 `approved`（`ListSpots` 里 `Status: model.FishingSpotStatusApproved`）。所以提交成功只进 `mySpots`，要看到它得去「我的钓点」页看审核状态。**别把成功提示写成「已添加」** —— 用户回头在地图上找不到，会以为丢了
- **改不了昵称** —— 服务端没有独立的改昵称接口。`saveNickname` 的做法是重新走一次微信登录带上昵称，服务端只在「这个账号昵称为空」时写入。已有昵称时 store 拦下，不让用户白等一次网络往返
- **`weather_indices` 曾恒为空** —— 那时后端没往外给，模型只能自己从温度气压反推，丢掉了「官方说今天适宜垂钓」这个最强的信号。现已接通
- **钓点纠错反馈不公开，提交者看不到状态** —— 这**不是缺口，是刻意的设计**：反馈未核实就公开会变成对钓点的舆论场。所以后端只给管理员留了队列端点，没有面向普通用户的读取端点，也没有「提交者查自己反馈」的端点。小程序这一侧因此没有「我的反馈」页面，提交成功只回一句「已提交，我们会核实」。⚠️ 别「顺手补一个查询端点」

## 约定细节

- **经纬度之外，坐标序列化也是两位小数**：`toLocationParam()` 是唯一出处
- **后端 `fxTime` 的截法只有一个出处**：`src/utils/date.ts` 的 `fxHourKey()`（13 位 `2026-10-26T01`）和 `fxMinuteKey()`（16 位 `2026-10-26T01:20`），配对的本地时间是 `localHourKey()` / `localMinuteKey()`。⚠️ **别自己写 `slice(0, 14)`** —— 第 14 位是分钟的冒号，切出来是 `2026-10-26T01:`，跟 13 位的字符串长度都不等，`findIndex` 永远返回 -1，「现在」那条竖线就不出现。逐时潮位按小时键对齐（数据是整点），潮时表按分钟键对齐（一天多条潮时，要分先后）
- **潮汐默认取离用户最近的站**：来源站随 `enriched` 响应带回（`tide_station`），潮汐图优先渲染这一份 —— 它是「用户所在地的潮汐」。港口切换是备选，编号是国家海洋预报台的站点编号（`HARBOR_OPTIONS`）。近站点 + 当天直接复用 `tide_data`，不再单独打一次潮汐接口
- **钓鱼反馈关联钓点 id**：反馈与记录在同一次提交里发出去，地点用记录那一份 —— 用户在钓点页选了哪个点，提交时既记到那个点头上，也记到那个点的记录上；没选过是 `'default'`（后端约定）
- **钓点的写操作走 `withSession`** —— `request` 只负责发请求，401 它直接抛，不会去刷 token。刷新那件事在 `api/client` 的 `withSession` 里。写入类端点全都要求登录，token 恰好是最容易过期的一枚，所以这几个都要包
- **用户不能给自己的钓点打分** —— 投稿时 `rating` 发 0（后端语义是「还没有评分」）。让作者自评会污染公开列表的均值

## 媒体

服务端返回的媒体路径一律是**相对路径**（如 `gallery/42/xxx.jpg`），显示前过 `api/upload` 的 `mediaUrl()` 拼成能加载的地址。已经是 `http` 开头的原样返回 —— 迁移过来的老数据可能是完整 URL。

**存进数据的必须是相对路径**，不是上传响应里的 `url`：那个字段已经带了 `/v3/media/` 前缀，再过一次 `mediaUrl()` 会变成双前缀地址；而完整 URL 则把部署域名烤进了库里，换域名时所有已存的图片一起失效。

上传端点 `POST /v3/upload` 的 multipart 字段是 `file`（文件）+ `type`（用途）。`type` 只认 `blog` / `gallery` / `feedback` / `record` / 空串，其余一律 400。**钓点照片走 `gallery`** —— 它会校验 Content-Type 白名单，`generic` 只限大小不认类型。**钓点纠错反馈的配图走 `feedback`** —— 落到 `feedback/{userID}/` 目录，与图片墙素材分开。**钓鱼记录的照片走 `record`** —— 落到 `records/{userID}/` 目录，与前两者都分开。

⚠️ 小程序加载远程图片走 **downloadFile 合法域名**，跟 request / uploadFile 是三份独立的名单 —— 见 `docs/mp-weixin-network.md` 的「微信后台配置」。

## 静态资源

**代码包里的**跟着每个用户下载，只放几乎每次打开都要用的图 ——
地图标记、tabBar 图标（都在 `src/static/`），小程序码在 `spot-detail` 分包里。

**CDN 上的**（`VITE_CDN_BASE_URL`）按需拉，只放少数场景才露面的图：
缺图占位插画（`SPOT_PLACEHOLDER_IMAGE`）与应用 logo（`APP_LOGO`）。
放进包里等于让所有人替少数人下载 —— 158KB 的插画和 15KB 的 logo 都不值。

⚠️ CDN 域名也要在微信后台配成 **downloadFile 合法域名** ——
`<image>` 的网络图和海报的 `canvas.createImage()` 走的是同一份名单。
体积、格式与产物表的细节见 `docs/mp-weixin-package.md` 的「静态资源」。
